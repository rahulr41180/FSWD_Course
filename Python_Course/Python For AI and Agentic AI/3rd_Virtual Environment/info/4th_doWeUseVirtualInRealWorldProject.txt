In real-world Python projects, developers almost always use a virtual environment.

Small Projects

Even for a simple Flask/FastAPI app:

python -m venv venv

Then:

pip install fastapi

This is standard practice.

Large Companies

Companies using:

Python
Django
Flask
FastAPI
AI/ML
Data Engineering

typically use:

venv
virtualenv
Poetry
Pipenv
Conda

for dependency isolation.

Example Team Workflow

Developer A:

git clone project
python -m venv venv
pip install -r requirements.txt

Developer B:

git clone project
python -m venv venv
pip install -r requirements.txt

Both get exactly the same environment.

Without venv

Imagine:

Python 3.12
Django 5.1
NumPy 2.0
TensorFlow 2.18

installed globally.

Now another project requires:

Django 4.2
NumPy 1.26

You may break one project while fixing another.

This is why teams avoid global package installation.

What About Docker?

Many modern companies use:

Docker

But even then, developers often create a virtual environment locally during development.

Typical setup:

Local Development
└── venv

Production
└── Docker Container
My Recommendation

As a developer:

Learning Python → venv optional
Personal projects → use venv
Freelance projects → use venv
Company projects → always use venv (or Poetry/Pipenv/Conda)

So if you join a Python project in a company, there's a very high chance you'll see something like:

python -m venv venv
source venv/bin/activate

or

poetry install

as part of the project setup.
