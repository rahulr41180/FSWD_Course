# Full Code

```js
const express = require('express');
const multer = require('multer');
const fs = require('fs');
const app = express();

// Set up multer to store uploaded files in memory
const upload = multer({ storage: multer.memoryStorage() });

app.post('/upload', upload.single('file'), (req, res) => {
    if (!req.file) {
        return res.status(400).send('No file uploaded.');
    }

    // req.file.buffer contains the binary data of the uploaded file
    const uploadedFileBuffer = req.file.buffer;

    fs.writeFile('uploaded_file.png', uploadedFileBuffer, (err) => {
        if (err) {
            return res.status(500).send('Error saving file.');
        }
        res.send('File uploaded and saved!');
    });
});

app.listen(3000, () => {
    console.log('Server running on port 3000');
});
```

# Interview Answer

If interviewer asks:

> Why is `multer.memoryStorage()` dangerous?

Answer:

> `memoryStorage()` stores the entire uploaded file in RAM as a Buffer. If multiple users upload large files simultaneously, memory consumption can grow rapidly, leading to high garbage collection overhead, degraded performance, and potentially crashing the Node.js process with an out-of-memory error. In production, disk storage or streaming uploads to services like S3 are generally preferred.

# Interview Question

If interviewer asks:

> Disk Storage vs Streams?

Answer:

### Disk Storage

```text
File is written to local disk.
Consumes little RAM.
Uses disk I/O.
Suitable for medium-sized uploads.
```

---

### Streams

```text
File is processed chunk by chunk.
Never loads the entire file into memory.
Extremely memory efficient.
Best for large files and cloud storage uploads.
```

---

One correction to remember:

People often say:

```text
Streams use zero RAM.
```

❌ Wrong.

Streams **do use RAM**, but only for a **small chunk at a time**, not for the entire file. That's why they scale so well.

# Example 1

Browser → Node → Disk

```js
const express = require('express');
const fs = require('fs');

const app = express();

app.post('/upload', (req, res) => {

    const writeStream = fs.createWriteStream(
        './uploads/file.bin'
    );

    req.pipe(writeStream);

    writeStream.on('finish', () => {
        res.send('Upload Complete');
    });

    writeStream.on('error', (err) => {
        console.log(err);
        res.status(500).send('Error');
    });

});

app.listen(3000);
```

Ek aur important baat:

Tumne bola:

> write method chunk1 ko createWriteStream destination per store kr dega

Thoda wording change karo.

`createWriteStream()` destination nahi hai.

Ye **destination ko represent karne wala Writable Stream object** hai.

```js
const writeStream =
    fs.createWriteStream('./uploads/file.bin');
```

```js

```

---

To short mein:

✅ Chunk1 aaya → pipe ne `write(chunk1)` call kiya → disk par likh diya

✅ Chunk2 aaya → pipe ne `write(chunk2)` call kiya → same file mein append ho gaya

✅ Chunk3 aaya → same process

✅ End aaya → `writeStream.end()` → `finish`

Tumhari understanding ab kaafi strong ho gayi hai. Agla important concept hai:

**Agar Chunk2 aane se pehle Chunk1 abhi disk par write hi ho raha ho, to Node kaise ensure karta hai ki data corrupt na ho?** Ye hume **internal buffering aur backpressure** tak le jayega. 🚀

# Code

Pehle code dekhte hain.

```js
const express = require('express');
const AWS = require('aws-sdk');
const { PassThrough } = require('stream');

const app = express();

const s3 = new AWS.S3({
    accessKeyId: 'YOUR_KEY',
    secretAccessKey: 'YOUR_SECRET',
    region: 'ap-south-1'
});

app.post('/upload', (req, res) => {

    const passThrough = new PassThrough();

    const uploadPromise = s3.upload({
        Bucket: 'my-bucket',
        Key: 'video.mp4',
        Body: passThrough
    }).promise();

    req.pipe(passThrough);

    uploadPromise
        .then(() => {
            res.send('Uploaded');
        })
        .catch(err => {
            console.log(err);
            res.status(500).send('Error');
        });
});

app.listen(3000);
```
